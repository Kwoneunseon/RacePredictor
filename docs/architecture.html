경마 자동 투자 봇 — 아키텍처

2. 단계별 설명

데이터 수집

  • library/collector_*.py — 말/기수/조교사/경주/경주결과/구간기록, 공공데이터포털 API
  • library/scraper_*.py — 배당/마체중, KRA 웹 스크래핑

전처리 · 피처 엔지니어링

  • core/preprocessor.py — 학습용 피처 전처리(라벨 인코딩 등)
  • core/feature_builder.py — DB에서 피처를 수집·계산해 DataFrame으로 반환
  • core/history_rebuilder.py — horse_race_history 테이블 재구성
  • core/race_filter.py — 베팅 대상 경주 필터링(거리/등급/두수 조건)

학습 · 캘리브레이션

  • core/trainer.py — XGBoost/LightGBM top3 분류기+ranker 학습, isotonic 캘리브레이션
  • core/model_manager.py — 학습된 모델 저장/로드 관리

확률 모델

  • core/rank_distribution.py — Harville(Plackett-Luce) 방식 top3/복연승 확률 유도. 구현·테스트 완료, 아직 예측·베팅 파이프라인에서 호출되지 않음(5. 알려진 구조적 이슈 참고)

예측

  • core/predictor.py — 오늘자 경주 예측 실행, 카카오톡 메시지 포맷 생성

베팅

  • core/ev_calculator.py — EV(기대값)/켈리 비율 베팅 계산
  • core/odds_collector.py — 배당 조회 파사드(library/scraper_odds.py 호출, 실패 시 DB 중앙값 fallback)
  • core/investor.py — 베팅 판단·기록(betting_records 저장)과 결과 정산

리포트

  • core/prediction_report.py — 예측 결과 HTML 리포트 생성
  • scripts/feature_importance_report.py — 변수 중요도 HTML 리포트 생성(main.py가 직접 호출, 학습 시마다 갱신)

실행 진입점

  • main.py — --mode {train,predict,update-results,tune} CLI
  • scheduler.py — APScheduler: 시간별/평일 06:00 데이터 수집, 매일 10:00 예측+카카오톡 전송

4. DB 마이그레이션 이력

스키마 상세는 각 SQL 파일 자체가 source of truth입니다. 여기서는 목록과 배경만 요약합니다.

  • 001_init_schema.sql — 최초 전체 스키마(horses/races/jockeys/trainers/race_entries 등 기본 테이블)
  • 002_retroactive_new_signal_tables.sql — 신호 피처 실험용 테이블(실험은 기각되었으나 재검토 가능성을 남기기 위해 스키마 유지). 테이블은 이미 운영 Supabase에 직접 생성돼 있어 이 파일 자체는 실질적인 스키마 변경 없이 그 상태를 재현하기 위한 기록용
  • 003_race_payouts.sql — 경주 확정배당(단승/연승/복승/쌍승/복연승/삼복승/삼쌍승) 저장 테이블 + 관련 인덱스
  • 004_betting_records_bet_type_check.sql — betting_records.bet_type에 CHECK 제약 추가(win/place 영문 어휘 통일, 이전에는 제약 없이 값 드리프트 위험 존재)

5. 알려진 구조적 이슈

아래 항목은 다음 단계(B: 경계 재정립 · A: 네이밍 정리)의 입력 자료입니다.

  • scripts/feature_importance_report.py를 main.py가 직접 import — “scripts는 core/library를 소비만 한다”는 레이어 원칙과 반대 방향
  • Utils/function.py — 이름만으로 내용을 알 수 없는 그랩백(grab-bag) 유틸리티 파일
  • core/odds_collector.py와 library/scraper_odds.py — 이름이 비슷하지만 레이어와 역할이 다름(전자는 core의 배당 조회 클래스, 후자는 library의 스크래핑 함수) — 새로 온 사람이 혼동하기 쉬움
  • core/rank_distribution.py(Harville 확률 모델) — 구현·테스트는 완료됐지만 core/predictor.py/core/investor.py 어디에서도 import되지 않아 예측·베팅 파이프라인과 연결돼 있지 않음
  • core/investor.py의 save_bets()/update_results() — betting_records 저장·정산 로직이 구현돼 있지만 main.py는 decide()만 호출함(실제 베팅 기록/정산은 아직 파이프라인에 연결 안 됨)
