# 신규 경주 신호 피처 3단계 롤아웃 — 최종 결과 (2026-07-20 데이터 버그 수정 후 재검증)

계획: `docs/superpowers/plans/2026-07-15-new-race-signal-features-plan.md`
백테스트 기간: 2026-05-01 ~ 2026-06-25 (408경주 고정)
원래 기준선 (Task 0 버그 수정 후): 단승 Precision@1 **42.9%**, 인기마(최저배당) 기준선 **20.8%**, 연승 top3_prob≥0.65 **79.9%** / 커버리지 69.6%

> **주의**: 이 문서는 2026-07-19에 작성된 초판을 대체한다. 초판의 1~3단계 개별 체크포인트는
> 아래 버그 2건 때문에 무효였다 — 사용자가 "학습 기간이 너무 짧아서 그런 것 아니냐"고 질문한 게
> 재점검의 계기가 되었다.

## 발견한 데이터 버그 2건 (핵심)

1. **race_id 트랙 라벨 불일치**: `race_entries`/`races`는 부산경남 트랙을 `"부산경남"`으로 쓰는데,
   API299 기반 `library/collector_race_detail.py`는 API가 반환하는 원본 `item["meet"]` 값
   `"부경"`을 그대로 race_id에 사용해 부산경남 경주(전체의 **30.7%**, 16,784/54,730건)의 신규
   피처 조인이 처음부터 전부 실패했다. 수정: 요청 시점에 이미 아는 meet 코드(1/2/3)로 canonical
   라벨을 강제(`MEET_LABEL`).
2. **PostgREST 기본 1000행 응답 제한**: `core/feature_builder.py`의 학습용 배치 조회들이
   race_id/horse_id를 500개씩 청크로 나눴지만 청크 **내부**에서 `range()` 페이지네이션을 하지
   않아, 한 청크에 실제 일치하는 행이 1000건을 넘으면(500 race_id × 평균 11마리 ≈ 5500행 예상)
   나머지가 조용히 잘려나갔다. `assigned_weight` 결측이 43,573/54,251건(80%)이나 됐던 원인.
   `_fetch_in_batches` 헬퍼로 청크+range() 페이지네이션을 함께 적용해 수정 → 결측 4,257건(8%,
   정상 범위)으로 감소. **기존 프로덕션 베이스라인 피처는 원래부터 올바르게 페이지네이션되어
   있어 이 버그의 영향을 받지 않았음을 확인.**

두 버그를 고치고 `race_entry_detail`(51,957건)을 재백필한 뒤 3개 피처군을 한 번에 켜서
재검증했다.

| 시나리오 | 단승 Precision@1 | 연승@0.65 (적중률/커버리지) |
|---|---|---|

| 3개 피처군 통합 (버그 수정 후 재검증) | 42.4% | 77.7% / 73.5% |

n=408 표준오차 ≈ ±2.4pp — 버그를 다 고친 뒤에도 개선이 노이즈 범위이거나 오히려 소폭 하락.
**데이터 품질 문제가 아니라 신호 자체가 이 모델에 유의미한 추가 정보를 주지 못한다는 결론에
이번엔 훨씬 높은 신뢰도가 있다.**

## 그 외 발견/수정한 버그 (재발 방지용으로 코드는 유지)

3. 말 통산 성적 필드명 오류: 계획서 가정(`ord1CntT`/`ord1CntY`/`rcCntT`/`rcCntY`)이 실제 API와
   달랐음. 진짜 필드는 `hrOrd1CntT`/`hrRcCntT`(통산만 존재, 최근1년 필드 없음). 기수/조교사
   필드는 계획서 가정이 맞았음.
4. `_join_section_records` 컬럼 충돌: `horse_section_records`도 `race_distance`/`horse_id`
   컬럼을 가져 `merge_asof`가 `_x`/`_y` 접미사를 붙이며 원본 컬럼이 사라짐.
5. 같은 메서드 인덱스 충돌: `merge_asof`가 결과에 새 `RangeIndex`를 부여, 말별 그룹 병합 후
   concat 시 인덱스 중복 → `sort_index()`가 서로 다른 말의 행을 뒤섞음. 인기마 기준선(모델과
   무관해야 함)이 20.8%→19.4%로 흔들린 증상으로 발견.
6. PostgREST 임베디드 조인 실패: `race_entry_detail`에 FK 제약이 없어 `races(...)/race_entries(...)`
   조인이 `PGRST200`으로 실패 → 수동 2단계 조회로 수정.
7. 통과순위/구간기록의 0값 함정: 짧은 거리에서 0은 "미해당"이지 실제 값이 아님.

## 교훈

- PostgREST 배치 조회는 청크 분할만으로는 부족하다 — 청크 내부까지 반드시 `range()`로
  페이지네이션할 것.
- PostgREST 관계 임베딩은 FK 제약이 없는 테이블에 쓰지 말고 항상 수동 조회+파이썬 병합을
  우선할 것.
- 외부 API가 반환하는 라벨 문자열(트랙명 등)을 그대로 조인 키로 쓰지 말고, 이미 알고 있는
  정규화된 값으로 canonical화할 것.
- 결과가 "노이즈 범위"로 나올 때는 데이터 파이프라인 자체를 의심해볼 것 — 이번엔 사용자의
  질문이 두 번째, 세 번째 버그를 찾아낸 계기가 되었다.
